# FAILURES.md — what broke, and what we changed

One line per problem: what we expected, what happened, what we did. This is the honest
history of the project (and the best viva preparation there is).

| Date | Expected | What actually happened | Fix |
|---|---|---|---|
| Sep 2026 | 8 GB laptop GPU | `nvidia-smi` showed RTX 3050 **6 GB**, only **5.1 GB free** (display + Windows reserve ~0.9 GB) | Chose the 2B model, 4-bit QLoRA, LoRA rank 8, gradient checkpointing, batch size 1, `--max-pixels` knob |
| Oct 2026 | Original 20 statements usable for page-level training | Ground truth had no page numbers — the model is trained page by page | `build_dataset.assign_pages()` recovers each row's page from the PDF text layer by matching balances in order |
| Oct 2026 | 20 statements (110 pages) enough to fine-tune | Far too few pages for a VLM; no generator code existed to make more | Wrote `generate.py`: 7 bank layouts, 5 spending profiles, page-level ground truth → 140 statements / 460 pages |
| Oct 2026 | `HoughLinesP` returns `(N,1,4)` | Newer OpenCV returned `(N,4)` → `cannot unpack non-iterable int32` | `lines.reshape(-1, 4)` |
| Oct 2026 | Deskew removes all tilt | Residual tilt ≈0.3–0.6° remains: perspective warp is not a pure rotation | Accepted; reported honestly (1.53° → 0.57° on heavy damage). Training on damaged copies makes the model robust to the rest |
| Oct 2026 | OCR baseline finds the table header | It matched the **summary boxes** ("TOTAL WITHDRAWALS … CLOSING BALANCE") first → debit/credit/balance columns wrong, balance accuracy 0% | Header line must contain no amounts and have debit < credit < balance from left to right |
| Oct 2026 | OCR baseline narration text | Words were glued together ("PENSIONDISBURSINGAUTH") | Join words within a line with spaces; join wrapped lines without |
| Oct 2026 | Generator never crashes | Empty counterparty name for some transaction types → `IndexError` in UPI handle builder | Fall back to a random handle when the name is empty |
| Oct 2026 | Tiny-model smoke test can over-fit one page | Loss only fell 6.35 → 6.23: a random 0.2M-parameter model cannot memorise 1,400 tokens | Changed the check to: LoRA gradient norm > 0 and loss falls; real capacity is tested on GPU |
| Oct 2026 | Corrector simulation is deterministic | Numbers moved by ±0.1 between runs (set iteration order changes with Python's hash seed) | Iterate the confusion pairs in sorted order |
| Oct 2026 | Classifier generalises equally on generated data | Unseen-bank accuracy 99.4% on generated data vs 95.7% on the original data | Generated narrations share merchant vocabulary across banks → easier. We report the original-data number as the honest one |
| Oct 2026 | Literature: arXiv 2410.01609 is "SynJAC" | The paper's current title is **DAViD** (same arXiv id, renamed) | Cite it under its current title |
| Oct 2026 | Dev environment can download Qwen2-VL | Hugging Face is blocked from the build environment | All model code smoke-tested with a tiny random Qwen2-VL; real runs happen on the laptop GPU / Kaggle |
| Nov 2026 | Loading Qwen2-VL in 4-bit (QLoRA) keeps the image intact | Code review before the first GPU run: transformers 4.51 casts the page image to the dtype of a vision-encoder weight, and a 4-bit weight is stored as `uint8` → the image reached the vision encoder as **4 integer values (0–255)** instead of real pixels. Reproduced on CPU with a tiny model. Training would have run on destroyed images and nothing would have crashed | Keep the vision encoder out of 4-bit (`llm_int8_skip_modules=["visual", "lm_head"]`, ~1 GB more memory), cast it back to fp16 after `prepare_model_for_kbit_training`, refuse to run if its dtype is not floating point. Regression test: `scripts/check_4bit_vision.py` |
| Nov 2026 | Anomaly test: a "spike" = a random past payment × 8–25 | A ₹50 tea × 20 = ₹1,000 is normal spending, not an anomaly; and "same amount twice on one day" also counted credits — shops receive identical UPI amounts all day (9.2% of original rows) | Spike = 3–10× the account's **largest ever** payment of that category; duplicates counted for **debits** only (0 natural duplicate debits in the data) |
| Nov 2026 | Train the Isolation Forest on the 140 generated statements | They are ~1 month long, so per-account averages were noisy and big normal payments (rent, fees) looked extreme: 1.8% false alarms on the 6-month originals, and the forest lost to a plain 3-sigma rule (AUC 90.1 vs 92.6) | Leave-one-statement-out on the 20 six-month originals |
| Nov 2026 | Isolation Forest alone catches every kind of anomaly | It caught 0% of amount spikes and 4% of duplicate debits: clean statements have no duplicate debits, so that feature is constant in training and a tree can never split on it; and forests are weak at points extreme in only one feature | Hybrid: forest OR duplicate-debit rule OR robust z-score > 3.5 → recall 27% → 62%, AUC 90.6 → 95.6 |
| Nov 2026 | Corrector on a real OCR'd statement (app test, PNB, 592 rows) | (a) a balance OCR missed entirely became 0.0 and could never be repaired; (b) row 143's balance was off by one digit (1→2, not in the confusion list) so it stayed broken, and the corrector then "fixed" row 144's **correct** credit 60 → 59 using that bad balance; (c) on the last row the closing-balance check ran *after* the balance was changed | Missing values are filled only when the next row confirms them; a balance fix that heals two rows may change any one digit (two equations agree); next to a failed balance only a pure column swap is allowed; closing check before the change. Simulation at 5%: auto-fixed 86.4 → 90.2%, wrong fixes 0.7 → 0.4%, clean rows damaged 2.2 → 0.0; Tesseract + corrector: unseen clean 97.4 → 98.0%, seen clean 99.2 → 100%. That statement: trust 92.7 → 98.1% |
| Nov 2026 | Balance-chain checking catches every misread | Tesseract misread a **run** of consecutive balances by the same +1 (…1.05 → …2.05). Inside the run every row still adds up, so wrong numbers verify; at the run's edge one fix aligned a correct value to the wrong neighbours (2 wrong fixes in 592 rows) | Known limit of arithmetic checking — stated in the report. A second reader (VLM vs OCR) disagreeing on the same row would catch it |
| Nov 2026 | Full fine-tuning run fits the Kaggle T4 (15 GB) | Run 1 crashed after ~2 h: `CUDA out of memory` in the backward pass (tried to allocate 3 GB with 1.15 GB free; 3 GB was reserved by PyTorch but unusable - fragmentation) | `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` + gradient checkpointing; the notebook now retries with smaller pages instead of failing. Run 2: 300 pages, 37 steps, best validation loss 0.060, peak 14.1 GB |
| Nov 2026 | Fine-tuned model output is clean JSON with 5 values per row | Error analysis of the test outputs: rows found 72-80%, but amounts right only 48-62%. (a) a stray quote (`],"["`) or a cut-off answer made the whole page fail to parse - the strict fallback kept only rows with exactly 5 values (one PNB page: 3 of 53 rows); (b) the model often copied an extra column (cheque/ref number, Axis "Init. Br") or dropped an empty cell, so every amount slid into the wrong field; (c) it copied the OPENING BALANCE line it was told to skip | Step 5a (`common.parse_model_output_tolerant`, `src/rowfix.py`): tolerant parsing + re-aligning values with the balance arithmetic. Same saved outputs, no retraining: new banks rows found 71.9 -> 96.1%, amounts right 61.8 -> 89.0%; seen banks 79.8 -> 91.3%, 48.0 -> 61.4%. Tesseract unchanged. Caveat: the rules were designed by looking at these test outputs, so the new demo statements are the fair check |
| Nov 2026 | Fine-tuned model reads clean pages best | On seen banks it found 63% of rows on clean scans but 95% on heavy-damage photos | Almost all of it was (a)+(b) above on two clean pages, not the image: with step 5a, clean 96.5% |
